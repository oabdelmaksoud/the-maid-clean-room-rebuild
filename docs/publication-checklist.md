# Publication checklist

## Local release candidate

- [ ] Confirm the distributed file list contains only intended original or explicitly permitted material.
- [ ] Inspect attribution, MIT license, source-exposure statements, and any later third-party reuse.
- [ ] Run the documented commands and full tests from a fresh directory.
- [ ] Copy only the skill directory and verify all its references and tools still work.
- [ ] Record supported Python/OS combinations actually tested and host trials actually observed.
- [ ] Have a separate reviewer inspect the package and resolve release-blocking findings.
- [ ] Inspect tracked and untracked files for private research, credentials, account material, absolute personal paths, and unwanted artifacts. Ignore rules alone do not prove exclusion.
- [ ] Check the final archive/tree and fresh-clone instructions; preserve exact revision and test evidence.

## Owner-authorized publication

- [ ] Confirm repository name, owner, visibility, and release scope with the owner.
- [ ] Obtain explicit authorization to publish or push this candidate.
- [ ] Configure the actual repository URL and available private reporting channel.
- [ ] Push the reviewed revision and observe its CI results.
- [ ] Create the intended release only after checks pass; verify its downloadable contents.

Local preparation, configured CI, or a completed checklist draft does not mean GitHub publication occurred. A release should describe tested compatibility and limitations rather than promise all-host support or product parity.
