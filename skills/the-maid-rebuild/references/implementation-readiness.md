# Implementation readiness for a selected slice

A safe packet, permission to develop known behavior, a ready slice and complete requested scope are separate decisions. Before implementing a new faithful slice, freeze canonical requirements and record applicable readiness. Continue independent ready backend work when unrelated visual evidence is blocked. Keep every requested surface and remaining discovery obligation visible; slice readiness does not authorize a narrower deliverable. Existing bounded examples need no migration to retain their earlier bounded claims.

## Prepare the slice

1. Keep sources in a ledger and derive atomic requirements with stable IDs. Review overlap, granularity and criticality; preserve mappings to historical contracts. Broad unknown surfaces remain discovery obligations.
2. Reconcile approved author/evaluator facts: surface, state, precondition, action, literal strings, enabled/disabled controls, navigation, persisted effect, recovery, evidence, confidence and acceptance IDs. Resolve conflicts before readiness.
3. Put the same canonical expected values in a hashed author-packet JSON artifact. Provide approved behavior facts, original wireframes and permitted measured specifications; retain restricted target captures outside the packet. Review semantics separately from exact field agreement.
4. Plan each real capability and its dependencies, authorized access, costs and target-relative journeys. Unavailable required capabilities block the applicable slice. A placeholder or differently named backend does not establish implemented behavior.
5. For visual slices, record matched capture conditions and a measured layout/type/color/spacing specification. Review tolerances and source restrictions before candidate execution. Nonvisual slices declare capture null.
6. Record separate inventory, packet and slice review evidence, an explicit target-specific task and resume record, and concrete blockers with owners and next actions.

## Local gate

Copy and complete the readiness templates, then run:

```sh
python3 skills/the-maid-rebuild/scripts/readiness.py PROJECT_DIR --json
```

The gate reads explicit `readiness-contract.json` and `readiness.json`, validates their exact versioned fields and hashes, and checks canonical/packet agreement, requirement/slice/capability coverage, recorded approvals, declared comparable captures, requested slice status and target identity. See [readiness record format](readiness-record-format.md). It uses the same bounded local file reader as the existing tools and does not execute services or contact the target. Exit 0 means the requested recorded slice gate passed; 1 means well-formed records are blocked; 2 means invalid records, integrity, paths or invocation.

`status: provisional` can pass for ready requested slices while other required slices remain nonready. Report the requested slice IDs and `required_nonready_slice_ids`; a passing slice gate does not establish full scope. `status: ready` cannot coexist with a nonready required slice. A full-scope readiness claim cannot coexist with nonready required scope or an open gap. `declared_scope_ready` describes the declared inventory only, not undiscovered product breadth.

The gate checks concrete control-state fields, exact expected snapshots in the author artifact, capture equality, declared available dependencies and target IDs in task/resume names. It cannot assess semantic adequacy, omitted controls, true independence, permission, actual service execution or measured geometry quality. Source IDs cannot double as requirement IDs; semantic duplicate-feature review still belongs to a reviewer. Acceptance IDs must map reciprocally to defined cases with canonical expectations and nonempty steps; these are definitions, not executed test evidence.

## Repair and retain history

A failed fidelity run moves to repair by default. Retain the old candidate/run and failures; create a new candidate identity. Record cause, owner, reproduction, requirement IDs, acceptance condition and next action. Closure requires a different repaired candidate, a reviewer distinct from the owner, hashed evidence and a rerun JSON artifact whose expected and actual values equal the frozen canonical values. That is a recorded-evidence check, not proof of runtime execution or immutable candidate bytes. Keep previous files outside the new record rather than overwriting history.

Fix accessible specified defects first. New target facts require a newly reviewed contract, not an edited oracle to hide a failure. If an access/dependency decision prevents further progress, leave an incomplete checkpoint with the concrete blocker. Use broader paired generation tasks and frozen quality rubrics from [verification and recovery](verification-and-recovery.md) to assess actual output quality.

REA remains optional. This gate grants no additional account, source, publication or side-effect authorization and makes no near-100-percent equivalence promise.
